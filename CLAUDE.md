# Xash3D hybrid core for MiSTer (Half-Life)

@hybrid/CLAUDE.md

## This core

- Name everywhere: `Xash3D` (core, folders, release), `xash3d` (game submodule, binary in `build/`, log, lock).
- The game is the `xash3d/` submodule, branch `mister`. Its MiSTer code is behind the `MISTER_HYBRID` build option.
- Build: `./build.sh` (game), `./core/build_core.sh` (FPGA), `./package.sh` (zip in `dist/`), `MISTER=root@<address> tools/deploy.sh`.
- Lines marked `GAME:` in the scripts and `TODO` in the READMEs are the places the template left for this game.

- Not on GitHub yet (Danik, 2026-10-14: local only): `xash3d/` is a plain clone of FWGS/xash3d-fwgs on a local branch `mister`, `hlsdk/` a clone of FWGS/hlsdk-portable, neither is a submodule. The forks, their `mister` branches and the core repository are still to be made; ask first.
- The engine is built with waf, not CMake (`build.sh`). `--static-linking=filesystem_stdio,ref_soft,menu` puts the engine's own libraries into the one binary, which has no position independent code and takes the static SDL2; `--mister-hybrid` (`MISTER_HYBRID`) keeps `dlopen` for the games' libraries (`engine/platform/misc/lib_static.c`, `posix/lib_posix.c`). A library that is linked in needs an `exports.txt` beside its `wscript`.
- The renderer is `ref/soft` (RGB565 through the window surface). No GPU, so `ref/gl` is not built.
- Each game has a folder next to the binary (`valve`, `bshift`, `gearbox`) and its client and server libraries come from a branch of hlsdk-portable (`build.sh`: folder, branch, server library name). The server library is named after `gamedll` in the game's `liblist.gam`, which is `hl.dll` for Blue Shift as well.
- `valve/extras.pk3` is the engine's own menu graphics and fonts (built with the engine), not game data: it is shipped.
- The MiSTer file is `xash3d/engine/platform/mister/mister_port.[ch]`. `MISTER_HYBRID_FPSLOG=1` logs the frames shown every 300 fields.
- Tests on the PC: game data pulled from the MiSTer into `data/` (ignored), `XASH3D_BASEDIR=$PWD/data MISTER_HYBRID_SHM=<file> build/host/xash3d -game bshift -ref soft -width 320 -height 200 +map ba_tram1` with `build/tools/fakecore <file> <script>`.
- Measured on the MiSTer, 2026-10-14, at 320x200: Blue Shift `ba_tram1` 34 to 58 frames per second, Half-Life `c1a0` (standing at the start) 45 to 50; 120MB of memory.
- Video: the menu and the console are 640x480 (interlaced on a 15kHz screen), the game is 320x200; `VID_MiSTerMode()` in `engine/client/vid_common.c` switches when the menu opens and closes (Danik's choice, 2026-10-14). The field of view and the software renderer's `yscale` take every mode as a 4:3 screen, so 320x200 is not stretched.
- Pad: `MiSTer_AddMappings()` in `engine/platform/sdl2/joy_sdl2.c` makes the core's joysticks SDL game controllers (J1 order = a, b, x, y, leftshoulder, rightshoulder, back, start; Menu OK / Back are the paddles and become Enter / Escape outside the game). The default bindings are the `MISTER_HYBRID` block of `engine/client/input/in_keys.c` and survive the `unbindall` of a `config.cfg` that came with the game.
- MiSTer presses the d-pad as well when the left stick is pushed far (Main_MiSTer does that for every core). The d-pad turns and the stick strafes, so in the game a d-pad press is dropped while the stick points its way (`MiSTer_StickHoldsDpad()`, `joy_sdl2.c`). In the menus both move, as they should.
- The menu shows the system's mouse pointer, which the core's SDL driver does not have: `V_MiSTerCursor()` in `engine/client/cl_view.c` draws an arrow where the mouse is, in the menu and the console.
- *Resolution* (status bit 25): the game in 320x200 or 320x240, `MiSTer_GameHeight()`, applied at once; `MISTER_HYBRID_HEIGHT=240` fixes it for a test. Nothing is scaled between the two: the HUD is the client library's, drawn pixel for pixel at its distances from the edges of whatever screen there is, and the loading screen is not shown in the game's mode at all but in 640x480 like the menu (not from one map to the next, where the last frame stays). Half-Life `c1a0` at 320x240 on the MiSTer: 41 to 43 frames per second (2026-10-14). The option itself was switched on the PC only (fakecore `osd 2000000`), not in the OSD.
- *Lock to 30 FPS* (status bit 26: Off, On) is this core's own, as in OpenScreamer (bit 28) and Dethrace (bit 26): the framework has no such switch, and Danik does not want it moved there (2026-10-14). Off is never more than one frame per field either (60), as every frame waits for the core's next field (`MiSTer_WaitFrame()`). An Auto setting (lock while frames came late, unlock when they were made with time to spare) existed for a day and was taken out at Danik's word: Off and On are all he wants (2026-10-14). `MISTER_HYBRID_LOCK30=0|1` fixes it for a test.

## Speed (2026-10-14)

- Measuring: `MISTER=root@<address> tools/bench.sh <name> <seconds> <game> +map <map>` runs the game on the MiSTer with `MISTER_HYBRID_FPSLOG=1` (frames per 300 fields, how many fields apart they came, milliseconds per stage, the slowest frame) and `MISTER_HYBRID_PROFILE=<file>` (the game thread's program counter, 1000 times per second of its CPU time; it costs 6%, `BENCH_NOPROFILE=1` leaves it out). `tools/profile.py build/bench/<name>.prof [<lines> [<stage>]]` and `tools/benchsum.py build/bench/*.log` read them. The MiSTer has no `perf`.
- Where a frame went before (Half-Life `c1a0`, 24.3ms): 3D view 17.7, server 2.8, conversion and copy to the window 1.3, the rest 2.5. By CPU time: models 25%, world spans 21%, world BSP and edges 19%, server and client state 13%. No single hot spot.
- What was done, same scene, 24.3ms to 18.7ms: ARM instead of Thumb instructions (`-marm`, engine and game libraries; 5%); `D_DrawSpans16` works the perspective out every 16 pixels, as its name says, not 8, and has no integer division left (the Cortex-A9 has none: `__divsi3`); opaque model meshes no longer go through the TriAPI (`R_StudioDrawNormalMeshFast`: a vertex is transformed once per submodel, no `fmodf` per texture coordinate; together 14% of the 3D view); a helper thread on the second core takes half of the solid surfaces' spans and of the conversion to the window (`ref/soft/r_jobs.c`; 2.7ms). `-Ofast` gained nothing for the renderer and is not used.
- Frames per second in 5 second windows, before and after: `c1a0` 41-43 / 53-57; Half-Life `c0a0` (tram) 32-59 / 43-59.6; Blue Shift `ba_tram1` 32-58 / 39-59.6. Light scenes hold every field (300 of 300); heavy ones do not, and will not with this renderer: the edge and model code that is left is one thread's work.
- The benchmark: `MISTER=root@<address> tools/benchmark.sh <name> [<environment>]` runs seven scenes (listed in the script: calm, tram, monsters, glass, models, water, light) for 40 seconds each and prints frames per second and milliseconds per stage. `tools/grab.py` (run by `bench.sh` with `BENCH_GRAB="<seconds>"`) saves the frame the core shows, which is how to see what a scene looks like on the MiSTer from here; `BENCH_KEYS` presses keys. `build/bench/findviews.py` was used to find maps whose start faces water or glass (it reads the BSPs in `data/valve/maps`).
- With monsters the game's logic was the frame, not the renderer: `c2a4a` 29ms of server in a 50ms frame, `c1a1b` 17 to 19ms. It was the engine's collision traces (`SV_ClipToEntity`, `PM_RecursiveHullCheck`, `SV_Move`), hardly the game library, and nearly all of them (8.2 of 8.7 million in a run) came from the pushers: every frame a lift, a train or a rotating brush moves (`SV_PushMove`, `SV_PushRotate`), Xash3D tested every entity of the map for being stuck (`SV_TestEntityPosition`, a whole trace) before it asked whether the entity was anywhere near the pusher, and the answer was thrown away for all that were not. `SV_PushMissesEntity()` (`sv_phys.c`) now asks first, for everything but clients, whose size that test sets: the same entities are pushed. Also `SV_ClipToEntity` asks first whether the entity's box is anywhere near the move, and the area tree has 64 leaves instead of 16 (`AREA_DEPTH` 6). `c2a4a` server 29ms to 8.8ms (25.7 to 35.8 frames per second), `c1a1b` 14.2 to 7.0ms (33.7 to 44.4). Not yet played: the pusher change is exact by reading, the area tree can change which of two entities hit at the same distance a trace reports.
- What is left of the server in `c2a4a` (8.8ms): point contents for every entity's water level (`SV_CheckWater`, `SV_WaterLinks` walks every solid entity of the area tree to find the few water brushes; about 1.6ms), the pushers' loop over every entity (each moving brush, every frame, about 0.8ms), sending the frame to the local client (delta encoding of about 70 entities, `AddToFullPack` of the game for 450), relinking. The traces themselves are about 2% of the CPU now.
- Water: only a brush entity can be water, so each area node has a second list beside `solid_edicts`, of its brush entities in the same order (`sv_brushnodes`, `sv_brushlinks` in `sv_world.c`, kept by `SV_LinkEdict` and `SV_UnlinkEdict`), and `SV_WaterLinks` walks that (2026-10-14). It gained little (2.7 to 2.4% of the game thread in `c2a4a`): most of what is in those lists are brushes anyway, doors and walls that are solid. Beside `areanode_t`, not in it: mods see that structure (`physint.h`). The same contents as the old walk in 600000 point tests (`c2a4a`, `c2a4b`, `c1a4d`, `c2a1a`, which have `func_water`). The pushers' loop over every entity is left as it is: it cannot be narrowed to the area tree exactly, entities that are in no list (not solid, but moving) are pushed too.
- `c1a1b` started with `+map` puts the player inside something: `PM_CheckStuck` of the game tries 54 positions every frame, on the client (stage input, 2.4ms) and the server (about 2ms). An artifact of the benchmark, played from `c1a1a` the landmark puts the player elsewhere.
- The first-person weapon and its HUD cost about 3ms of the 3D view (`c1a0` with and without `impulse 101`).
- Options that trade the picture for speed were tried and dropped (Danik, 2026-10-14: no noticeable difference): textures of half the size from half the distance (`sw_mipscale 2`), no dynamic lights (`r_dynamic 0`), water without waves and glass every second pixel instead of blended. Each was worth 0.1 to 0.6ms of the 3D view in the benchmark's scenes.
- NEON span drawing was tried and dropped (2026-10-14). With the helper thread the game thread spends 8% of its time in span jobs and 0.2% waiting for the helper (`c1a0`): spans are hardly on the frame's path, the edges, models and the BSP are. And on the Cortex-A9 NEON did not make them faster: it cannot gather texels, and texel offsets worked out in NEON and read back by the integer core were 70% slower than the C loop (a micro-benchmark on the MiSTer). Half of a span's cost is its perspective every 16 pixels, not the pixels (spans are 18 to 27 pixels on average, half of them 8 or less); a version that let the float unit work out the next point while the integer core drew (as Quake did on the Pentium), with s, t and z as one vector, gave the same pixels and the same time: the compiler moves values between the float and NEON registers through the integer ones, and the in-order NEON queue stops behind the division. Z spans alone in NEON are twice as fast (8 at a time), worth about 0.4ms of a frame without the helper and nothing with it. What would count is giving the helper more of the game thread's work (it idles most of the frame): the models, next point.
- The opaque studio models of the solid entities are drawn on the helper (2026-10-14, `r_studio.c`, "STUDIO MODELS ON THE HELPER THREAD"): `R_StudioDrawPoints` copies what a submodel needs of `g_studio` (bones, light, the view's transform) into a job and returns, the game thread goes on with the client library's next model. The triangle code's globals (`r_polyse.c`, `r_aclip.c`, `r_affinetridesc`) belong to the jobs from `R_StudioJobsBegin` to `R_StudioJobsEnd` (the solid entity loop of `R_DrawEntitiesOnList`): the game thread finishes the jobs (`R_StudioJobsSync`) before `GL_Bind`, `TriBegin`, a brush entity or a model the jobs do not draw (translucent, glow shell, float texture coordinates, bone weights). The jobs run one at a time in the order they were added (`R_JobsOrdered`, models draw over each other), on the helper; on the game thread only if the helper had not started when the game thread got to the end. Chrome meshes (Barney) are drawn by the jobs too, else each would make the game thread wait in the middle. The weapon is not a job (nothing is left to do meanwhile). Checked on the PC by drawing every submodel both ways and comparing the frame and the z-buffer: 0 pixels of 150000 submodels differed (2026-10-14).
- `R_StudioDrawNormalMeshFast` (and the job's copy) took a quarter of its time converting the texture coordinates of each strip vertex from float, every frame: `R_StudioSkinCoordTable()` has them for every texel of a skin size, made once with the same expression. The light of a vertex without local lights is the light of its normal, worked out once per normal (`g_normlight`). Both exactly as before (31 million coordinates compared).
- A model job is two stages (2026-10-14): the vertices (bones, light, projection into buffers of the job's own, `R_StudioJobVertices`) and the triangles. Either thread can do the first: when the game thread would wait for the helper (`R_StudioJobsSync`, `R_StudioJobsEnd`), it does the vertices of the jobs the helper has not got to, from the last one back (`R_StudioJobsHelp`); the helper does them itself for the rest (`stage`, taken with an atomic exchange). The bone caches of the vertex stage are per thread (`__thread`).
- `R_StudioSkinCoordTable` had a bug until 2026-10-14: with more than 32 skin sizes in a frame (a gargantua and scientists) the t table could take the place of the s table of the same mesh, and a mesh got wrong texture coordinates. It now keeps 64 and throws out the one asked for longest ago. Found by drawing every submodel both ways with a gargantua spawned next to the player (`sv_cheats 1`, `sv_enttools_enable 1`, `ent_create monster_gargantua`): its flames are the only local lights (`TE_ELIGHT`) Half-Life makes besides the alien controllers', so that is also how the jobs' local light path was checked (829 jobs with local lights, 7822 with chrome, 42000 submodels, no pixel different).
- Render time with the models on the helper, MiSTer, 2026-10-14: lobby (`c1a0`) 12.9 to 11.8ms, tram 11.7 to 10.1, monsters 14.9 to 13.0, models 11.9 to 10.5, weapon and flashlight 15.8 to 14.9.
- The world's edge scan (`R_ScanEdges`) is shared (2026-10-14, `r_edge.c`, "THE LOWER ROWS ON THE HELPER THREAD"): the game thread copies the frame's edges and scans the upper rows; the helper steps the copy through those rows without making spans (the order of edges at the same u is that history, so the table is exactly the same) and makes the spans of the lower rows into a buffer and a surface stack of its own, which `R_HScanJoin` puts into the surfaces' lists before they are drawn. Where the frame splits moves by two rows a frame towards an even share. If the helper's spans do not fit, the game thread scans the lower rows itself. Checked on the PC by scanning every frame both ways and comparing the frame and the z-buffer: nine maps at 320x200 and 320x240, and with both span buffers made small so that both rare paths ran, no pixel different.
- The client's first message of a connection marked every sequence number from 1 up to the server's random first one (up to 2^27) as dropped: tens of millions of loops, about two seconds on the MiSTer before the first frame of a map (`CL_ParseClientData`). It marks the last `CL_UPDATE_BACKUP`, which are all the slots there are (2026-10-14).
- Profile guided optimisation (2026-10-14): `MISTER=root@<address> tools/pgo.sh` builds the engine with counters (`PGO=generate ./build.sh`), runs the benchmark's seven scenes with it on the MiSTer (the counts are written to `/tmp/xash3d-pgo` there when the game quits, which the benchmark's kill does), fetches them into `build/pgo` and builds again with them. `build.sh` uses `build/pgo` whenever it is there (`PGO=off` builds without). `-fprofile-partial-training`: code the scenes did not reach is optimised as without a profile, not for size. The counts are of the code as it was: run `tools/pgo.sh` again after larger changes to the engine. The games' libraries are not built with a profile.
- This round, each step against the one before it, run in turns scene by scene on the MiSTer (2026-10-14; frames per second, lobby / tram / monsters / models / glass): model vertices shared out, 3D view 1.1 to 1.9ms less; edge scan split, 0.24 to 0.5ms less (monsters 39.8 to 40.8); PGO, 5 to 8% less work in every stage (59.5 / 58.3 / 40.1 / - / 44.6 to 59.6 / 59.0 / 42.2 / 59.4 / 48.8). The lobby now holds 298 to 299 frames of 300 fields. Measured conditions vary: a Sony controller's kernel thread (`khidpd_054c0ce6`) took half a core for a while and every stage was 5 to 8% slower meanwhile, so compare builds in turns, not with an older run.
- CPU1 is never idle: Main_MiSTer spins on it. The helper thread sleeps except while there are spans to draw, and yields while it waits for the next one.
- The framework's controller scan (`hybrid/hps/mister_triggers.c`, every 2 seconds) opened every `/dev/input/event*` that is no gamepad again each time, and the game stood still for 40 to 60ms: a frame three or four fields late every two seconds, in every core built since the triggers went in (2026-10-12). It now remembers them by inode and time. **This change is in the `hybrid/` working tree only, not committed or pushed**: ask Danik. The other cores get it by being built again.
- `build.sh` removes the linked binary before `waf build`: waf does not relink when only the static SDL2 (with the hybrid library in it) has changed.
- The launch script keeps the log in `/tmp` while the game runs and appends it to `/media/fat/logs/Xash3D/xash3d.log` when the game has left: a line printed to the card is a write of about 9ms. The template has it too since Hybrid_MiSTer `main` of 2026-10-14; the cores stamped before that still write to the card directly and get the lines at their next release.
- The game list (`MiSTer_SelectGame()`, before the engine starts) shows the folders that have a `liblist.gam` and our client library; `valve` has to be there for any of them.
- The engine prints nothing without `-console` or `-dev`; with `MISTER_HYBRID` `Con_Printf` always prints, so the launcher's log has it.
- The SD card is mounted `sync`: every `write()` waits for the card. The engine printed its configs a line at a time, so quitting took 6.5 seconds; `filesystem/io.c` now collects what `FS_Printf` and `FS_Print` write (`FS_FlushPrint()`), and quitting takes 0.7. A game that is still on its way out when the next one starts takes the screen from it as it closes (`MH_Close()` clears the control block): that is how the game list came to be missing on 2026-10-14, after a restart over ssh four seconds after a kill. On the MiSTer, test sequences that kill the game go into a detached script (`setsid nohup`), the ssh session does not always survive them.
