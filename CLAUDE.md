# Xash3D hybrid core for MiSTer (Half-Life)

@hybrid/CLAUDE.md

## This core

- Name everywhere: `Xash3D` (core, folders, release), `xash3d` (game submodule, binary in `build/`, log, lock).
- The game is the `xash3d/` submodule, branch `mister`. Its MiSTer code is behind the `MISTER_HYBRID` build option.
- Build: `./build.sh` (game), `./core/build_core.sh` (FPGA), `./package.sh` (zip in `dist/`), `MISTER=root@<address> tools/deploy.sh`.
- Lines marked `GAME:` in the scripts and `TODO` in the READMEs are the places the template left for this game.

<!-- Notes that are only true for this game go below. -->

- Not on GitHub yet (Danik, 2026-10-14: local only): `xash3d/` is a plain clone of FWGS/xash3d-fwgs on a local branch `mister`, `hlsdk/` a clone of FWGS/hlsdk-portable, neither is a submodule. The forks, their `mister` branches and the core repository are still to be made; ask first.
- The engine is built with waf, not CMake (`build.sh`). `--static-linking=filesystem_stdio,ref_soft,menu` puts the engine's own libraries into the one binary, which has no position independent code and takes the static SDL2; `--mister-hybrid` (`MISTER_HYBRID`) keeps `dlopen` for the games' libraries (`engine/platform/misc/lib_static.c`, `posix/lib_posix.c`). A library that is linked in needs an `exports.txt` beside its `wscript`.
- The renderer is `ref/soft` (RGB565 through the window surface). No GPU, so `ref/gl` is not built.
- Each game has a folder next to the binary (`valve`, `bshift`, `gearbox`) and its client and server libraries come from a branch of hlsdk-portable (`build.sh`: folder, branch, server library name). The server library is named after `gamedll` in the game's `liblist.gam`, which is `hl.dll` for Blue Shift as well.
- `valve/extras.pk3` is the engine's own menu graphics and fonts (built with the engine), not game data: it is shipped.
- The MiSTer file is `xash3d/engine/platform/mister/mister_port.[ch]`. `MISTER_HYBRID_FPSLOG=1` logs the frames shown every 300 fields.
- Tests on the PC: game data pulled from the MiSTer into `data/` (ignored), `XASH3D_BASEDIR=$PWD/data MISTER_HYBRID_SHM=<file> build/host/xash3d -game bshift -ref soft -width 320 -height 200 +map ba_tram1` with `build/tools/fakecore <file> <script>`.
- Measured on the MiSTer, 2026-10-14, at 320x200: Blue Shift `ba_tram1` 34 to 58 frames per second, Half-Life `c1a0` (standing at the start) 45 to 50; 120MB of memory.
- Video: the menu and the console are 640x480 (interlaced on a 15kHz screen), the game is 320x200; `VID_MiSTerMode()` in `engine/client/vid_common.c` switches when the menu opens and closes (Danik's choice, 2026-10-14). The field of view and the software renderer's `yscale` take every mode as a 4:3 screen, so 320x200 is not stretched.
- Pad: `MiSTer_AddMappings()` in `engine/platform/sdl2/joy_sdl2.c` makes the core's joysticks SDL game controllers (J1 order = a, b, x, y, leftshoulder, rightshoulder, back, start; Menu OK / Back are the paddles and become Enter / Escape outside the game). The default bindings are the `MISTER_HYBRID` block of `engine/client/input/in_keys.c` and survive the `unbindall` of a `config.cfg` that came with the game.
- MiSTer presses the d-pad as well when the left stick is pushed far (Main_MiSTer does that for every core). The d-pad turns and the stick strafes, so in the game a d-pad press is dropped while the stick points its way (`MiSTer_StickHoldsDpad()`, `joy_sdl2.c`). In the menus both move, as they should.
- The menu shows the system's mouse pointer, which the core's SDL driver does not have: `V_MiSTerCursor()` in `engine/client/cl_view.c` draws an arrow where the mouse is, in the menu and the console.
- *Resolution* (status bit 25): the game in 320x200 or 320x240, `MiSTer_GameHeight()`, applied at once; `MISTER_HYBRID_HEIGHT=240` fixes it for a test. Nothing is scaled between the two: the HUD is the client library's, drawn pixel for pixel at its distances from the edges of whatever screen there is, and the loading screen is not shown in the game's mode at all but in 640x480 like the menu (not from one map to the next, where the last frame stays). Half-Life `c1a0` at 320x240 on the MiSTer: 41 to 43 frames per second (2026-10-14). The option itself was switched on the PC only (fakecore `osd 2000000`), not in the OSD.
- *Lock to 30 FPS* (status bits 27:26: Off, On, Auto) is this core's own, as in OpenScreamer (bit 28) and Dethrace (bit 26): the framework has no such switch, and Danik does not want it moved there (2026-10-14). Auto (`PaceAuto()` in `mister_port.c`) locks when 6 of the last 60 frames were a field late and unlocks when all but 3 of the last 120 were made with half a millisecond to spare; on the Blue Shift tram ride every 5 second window was then either 150 frames two fields apart or 300 one apart, with one window of change between. Tried with `MISTER_HYBRID_LOCK30=0|1|2`, not from the OSD.

## Speed (2026-10-14)

- Measuring: `MISTER=root@<address> tools/bench.sh <name> <seconds> <game> +map <map>` runs the game on the MiSTer with `MISTER_HYBRID_FPSLOG=1` (frames per 300 fields, how many fields apart they came, milliseconds per stage, the slowest frame) and `MISTER_HYBRID_PROFILE=<file>` (the game thread's program counter, 1000 times per second of its CPU time; it costs 6%, `BENCH_NOPROFILE=1` leaves it out). `tools/profile.py build/bench/<name>.prof [<lines> [<stage>]]` and `tools/benchsum.py build/bench/*.log` read them. The MiSTer has no `perf`.
- Where a frame went before (Half-Life `c1a0`, 24.3ms): 3D view 17.7, server 2.8, conversion and copy to the window 1.3, the rest 2.5. By CPU time: models 25%, world spans 21%, world BSP and edges 19%, server and client state 13%. No single hot spot.
- What was done, same scene, 24.3ms to 18.7ms: ARM instead of Thumb instructions (`-marm`, engine and game libraries; 5%); `D_DrawSpans16` works the perspective out every 16 pixels, as its name says, not 8, and has no integer division left (the Cortex-A9 has none: `__divsi3`); opaque model meshes no longer go through the TriAPI (`R_StudioDrawNormalMeshFast`: a vertex is transformed once per submodel, no `fmodf` per texture coordinate; together 14% of the 3D view); a helper thread on the second core takes half of the solid surfaces' spans and of the conversion to the window (`ref/soft/r_jobs.c`; 2.7ms). `-Ofast` gained nothing for the renderer and is not used.
- Frames per second in 5 second windows, before and after: `c1a0` 41-43 / 53-57; Half-Life `c0a0` (tram) 32-59 / 43-59.6; Blue Shift `ba_tram1` 32-58 / 39-59.6. Light scenes hold every field (300 of 300); heavy ones do not, and will not with this renderer: the edge and model code that is left is one thread's work.
- CPU1 is never idle: Main_MiSTer spins on it. The helper thread sleeps except while there are spans to draw, and yields while it waits for the next one.
- The framework's controller scan (`hybrid/hps/mister_triggers.c`, every 2 seconds) opened every `/dev/input/event*` that is no gamepad again each time, and the game stood still for 40 to 60ms: a frame three or four fields late every two seconds, in every core built since the triggers went in (2026-10-12). It now remembers them by inode and time. **This change is in the `hybrid/` working tree only, not committed or pushed**: ask Danik. The other cores get it by being built again.
- `build.sh` removes the linked binary before `waf build`: waf does not relink when only the static SDL2 (with the hybrid library in it) has changed.
- The launch script keeps the log in `/tmp` while the game runs and appends it to `/media/fat/logs/Xash3D/xash3d.log` when the game has left: a line printed to the card is a write of about 9ms. The template has it too since Hybrid_MiSTer `main` of 2026-10-14; the cores stamped before that still write to the card directly and get the lines at their next release.
- The game list (`MiSTer_SelectGame()`, before the engine starts) shows the folders that have a `liblist.gam` and our client library; `valve` has to be there for any of them.
- The engine prints nothing without `-console` or `-dev`; with `MISTER_HYBRID` `Con_Printf` always prints, so the launcher's log has it.
- The SD card is mounted `sync`: every `write()` waits for the card. The engine printed its configs a line at a time, so quitting took 6.5 seconds; `filesystem/io.c` now collects what `FS_Printf` and `FS_Print` write (`FS_FlushPrint()`), and quitting takes 0.7. A game that is still on its way out when the next one starts takes the screen from it as it closes (`MH_Close()` clears the control block): that is how the game list came to be missing on 2026-10-14, after a restart over ssh four seconds after a kill. On the MiSTer, test sequences that kill the game go into a detached script (`setsid nohup`), the ssh session does not always survive them.
- Still open: every `TODO` of the READMEs; the menu has no entry selected until the d-pad is pressed once; colour codes in the log; music, saved games, keyboard and mouse were not tried on the MiSTer; Opposing Force and Blue Shift were started, not played.
